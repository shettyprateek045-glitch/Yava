    Why the Decision Threshold Matters

    At the default 0.5 cutoff, this model rarely predicts churn at all — recall collapses to roughly 5%, meaning it misses nearly every customer who actually churns. Optimizing the threshold for F1 instead lifts recall substantially, which matters here because in a retention use case a missed churner is far costlier than one wasted outreach email. The threshold shown below (and used throughout this console and the API) is that optimized value — not 0.5.

    About This Model

    This console sits on top of a four-week churn-prediction project for a hypothetical subscription streaming service. It scores the likelihood that an active subscriber cancels, so a retention team can prioritize outreach toward the accounts most likely to leave.

    Training data: a synthetic dataset generated for this project (Week1_Project_Planning/generate_dataset.py) — not real subscriber records, and not validated against real-world behavior.

    Intended use: a prioritization signal for a human retention team, not an automated accept/reject system.

    Full methodology, feature list, and an honest before/after comparison of the model versions live in MODEL_CARD.md at the repository root. Known gaps and the recommended next-stage build-out are documented in ADVANCED_VERSION.md.
